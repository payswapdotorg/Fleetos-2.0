## 2. Scope

Freeze the **smallest real, auditable marketplace pilot** that can exercise:

`real need → verified offer(s) → policy-governed approval → actual supplier commitment/order → fulfilment/service evidence → receipt/acceptance → authoritative asset/lifecycle record`.

At this stage, freeze product/state/API/ownership/acceptance contracts and dispatchable implementation packets. Do not build the entire marketplace in F360; do not add speculative provider code or claim the pilot already exists.

## 3. Market and supplier feasibility — evidence first

Choose one market and a minimal initial category set based on evidence of access to at least one real business customer and independently verifiable suppliers. Categories should include end-user computing plus one operational category (e.g. printers/photocopiers or networking gear), unless the feasibility record explains a narrower starter and the extension plan.

For each candidate customer/provider record only non-sensitive, verified facts needed for feasibility: contact/status reference (no secrets or personal data in Git), geographic coverage, categories, how inventory/pricing/quotes can be supplied, fulfilment/repair capability, warranty/returns, and what can be manually verified during a pilot. Record source and date. Do **not** invent partner names, availability, commercial terms, APIs or commitments. If no actual supply/customer access can be substantiated, record the live-pilot gate as BLOCKED and add supplier/customer acquisition work rather than pretending a fixture proves access.

A manually operated supplier adapter or reviewed catalogue import can be an MVP seam if plainly labelled, source/freshness tracked and operator-auditable. It is not a claim of automated or live API integration.

## 4. Freeze contracts and state machines

The decision document must map existing contracts and authoritative owners before designing additions. At minimum, decide and document:
- canonical IDs and tenant/site/actor context;
- request/need schema and lifecycle states;
- equipment category/specification and compatibility constraints;
- supplier verification/suspension state, catalogue/SKU, stock/availability evidence and expiry;
- offer/quote schema, currency, line cost, tax/shipping/fees, delivery estimate, condition, warranty/support, validity window and source reference;
- transparent eligibility rules and explainable offer comparison; separate hard constraints from preference weights;
- approval/Guardian request, limits, evidence and actor authorization;
- order / rental / lease / repair-service contract boundary and source status;
- provider ack / webhook / manual verification, idempotency, retry and reconciliation rules;
- shipment/service milestones, receipt, discrepancy, cancellation/return/dispute where the pilot supports them;
- asset enrollment/link after accepted receipt, duplicate serial/asset guard, custody, warranty and lifecycle events;
- audit/evidence retention, artifacts, observability, failure/recovery, degraded and unavailable states.

Use existing bounded contexts and public contracts wherever they fit. Do not introduce duplicate supplier, asset, order or audit truths across domains. Any new contract must be represented in types, decision notes and tests in the owning context. Update `spec/DEPENDENCY-GRAPH.md` and generated contract snapshots only if the frozen architecture requires them, and document the impact.

## 5. Persistence, identity and money movement

- PostgreSQL/domain persistence remains the intended authoritative business store per Architecture Lock. F351A's JSONL service proves only its documented operational subset and is not approval for marketplace transaction storage.
- Do not add a new authoritative persistence system without the explicit operator gate and ADR required by `FLEETOS-SOURCE-OF-TRUTH.md`.
- Production pilot requires authenticated identities and server/domain-side tenant authorization; the demo actor shape/scope checks are not authentication.
- Payment/escrow/credit/financing are outside MVP unless a real suitable provider plus legal/compliance/risk review is established. F360 must specify the order/invoice/manual-settlement boundary without simulating actual money movement.
- Aurum, ADCOS and Arena remain `CONTRACT_ONLY` unless independent live/sandbox evidence changes that status.

## 6. Worker plan and ownership

Create packet files before dispatch, respecting `spec/worker-ownership.yaml` and the three-worker limit:

- **F361A / Worker A — receive and reconcile equipment into asset truth.** Scope only A-owned asset/device/observation/field paths and evidence. Receipt evidence links serial/tag, tenant/site, owner, warranty and lifecycle to one authoritative asset; prevent duplicate registration; failure/discrepancy paths are auditable.
- **F361B / Worker B — trust, Guardian, security and evidence controls.** Scope B-owned verification/policy/action/evidence/security paths and evidence. Supplier claims/source freshness, role/limit checks, approval/refusal, audit/evidence requirements, and untrusted/duplicate provider events have fail-closed tests. Do not implement supplier/order truth in B's package.
- **F361C / Worker C — supplier, catalogue, offers, procurement and fulfilment contract.** Scope C-owned vendor/procurement/work paths and commerce acceptance/evidence. Supplier profile and pilot ingestion, current offer/quote, comparison/selection, order/service states, external/manual confirmation and reconciliation have real public-domain-API tests.
- **TL — shared contracts, web UI/application composition, infrastructure, migration/storage wiring, provider credentials/secrets, integration, browser E2E, deployment and acceptance.** Do not delegate TL-owned shell/infrastructure by assumption; if cross-path implementation is required, the TL owns that work or creates a narrow recorded grant.

Freeze public contracts and path boundaries before any F361 work begins. Packets must specify exact files, dependencies, test commands, evidence paths and forbidden paths. Run A/B/C concurrently only after their inputs are frozen and their owned paths are disjoint.

## 7. End-to-end acceptance design

The freeze must define one deterministic automated journey that uses real local public domain APIs and one separate live/staging acceptance protocol. Local tests may use deterministic fixtures for repeatability, but report them as fixture/contract-tested, not live supplier proof.

The required live pilot path is documented in `docs/product/UBER-FOR-COMPANY-IT-EQUIPMENT.md` §8. The acceptance plan must cover at least:
- real request through UI;
- supplier/source-verified offer and fresh availability; at least two offers where feasible, or an honest single-offer exception;
- role-specific comparison and approval;
- real supplier acknowledgement or independently captured fulfilment evidence;
- real delivery/service and acceptance/exception evidence;
- asset enrollment/link and serial/duplicate guard when equipment is involved;
- tenant isolation, authentication, Guardian, idempotency, audit and recovery;
- mobile/role-aware UI states, including stale/unavailable/refused/error;
- exact-candidate deployment and all relevant tests/builds;
- measurable business outcomes: quote response, request-to-decision, fill rate, on-time fulfilment/service, cost baseline, exception rate and feedback.

No screenshot, simulated provider response, worker report or local green test alone satisfies the live pilot gate.

## 9. Exit criteria

F360 is complete when the scope is realistic and evidence-grounded, contracts/authority/ownership are frozen, the three implementation packets are standalone and non-overlapping, the live-pilot gate is testable, all repository records agree, and unresolved real-customer/supplier access is explicitly recorded as a blocker rather than assumed. Only then dispatch F361A/B/C.

The destination is the neutral equipment and service marketplace. F360 must not mark procurement, fulfilment, authentication, supplier networks, payments or predictive optimization as implemented; it freezes how the team will prove them.
