## The service (Q1)

One Node process, fixed port **3106**, serving BOTH:

1. the static shell — `packages/web/dist-fleetos/` (build with
   `npx vite build --config vite.fleetos.config.ts` from `packages/web`;
   the build injects `__FLEETOS_COMMIT__` — build at your lane-tip SHA so
   the footer proves the candidate), hash routing, SPA fallback; and
2. the durable API — the operational plane, append-only JSONL segments
   under `infrastructure/fleetos-durable/data/`:
   - `commands.jsonl` — the REAL command-queue records the UI submits
   - `audit.jsonl` — the submission audit-log entries
   - `assets.jsonl` — asset enrollments

Laws: write-before-ack (the record is on disk before the HTTP response);
replay-on-start (the service rebuilds its in-memory state by replaying the
segments); idempotency EXACTLY as the in-process contract (a duplicate
logical intent returns `duplicate=true`, never a second enqueue);
tenant-scoping fail-closed (a tenant-scope mismatch refuses — never leaks
cross-tenant records). Keep the service small and readable: `node:http`,
no framework.

## The shell durable mode (Q1 continued)

Add a durable-mode binding to the fleetos composition: an adapter that
implements the SAME port contracts the in-process composition uses
(`commandPath.ts` — the submit port, the queue-records read, the audit
read; the enrollment path the pages drive). In durable mode the browser
submits to the service (`POST` the draft, receive the ack/refusal) and
reads records back (`GET` per tenant). The fixture WORLD stays the
domain-input convention (observations, sim-worlds — Q4); the OPERATIONAL
plane (commands, audit, enrollments) goes durable. Toggle by build flag or
query param — the in-process mode must keep working (the acceptance
suites' composition is untouched).

## The restart-recovery proof (Q2 — machine-run, in your report)

A script (`infrastructure/fleetos-durable/proof-restart.sh` or .mjs) that:
1. starts the service, drives a seed sequence through the API (enroll 2
   assets across 2 tenants, submit 3 commands incl. one duplicate and one
   refused),
2. captures the full record-set digest (sha256 over the canonical JSON of
   all records, per segment and total),
3. `kill -9` the service, restart it,
4. re-reads through the API and re-digests — **byte-exact match required**,
5. exits 0 only on match; prints every digest.
