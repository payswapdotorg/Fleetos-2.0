# F370B — secret management: the rotating keyring, session revocation, host-boundary randomness (Worker B, Wave 18)

## Mission

The F370A honest limitation, now due: the pilot signing key is a
plainly-labelled fixture and the credential salt is caller-supplied. This
lane makes key lifecycle REAL at the boundary the Architecture Lock allows:
a **rotating keyring** (issue under the current key, verify by the key id
carried in the token, old keys verifiable through a grace window, refused
after retirement), **session revocation** (a jti claim + a revocation
registry composed into verification — verdicts-as-data, never exception
control flow), and the **host-boundary randomness port** (salt and key
material generated through an injected SecureRandom; the domain stays
deterministic-under-injection — the repo law). NO new authoritative
business store (Architecture Lock): the keyring is configuration-class
(file/env-backed providers, plainly labelled; real KMS stays honestly
BLOCKED and recorded); the revocation registry is in-memory and plainly
labelled (persistent revocation is F370C/server-wiring class). Provider
credentials and key material NEVER in bundles, logs, errors, or journey
output — machine-asserted.

## Deliverables (all in your owned paths)

1. **The rotating keyring** (`packages/identity/src/keyring.ts`):
   - `KeyringProvider` port: `currentKeyId()`, `resolveKeyMaterial(keyId)`
     (hex or bytes — your choice, frozen in your contract), `listKeyIds()`;
   - `RotatingKeyring` composition over the port: issue binds the current
     key id INTO the token (header segment or claim — your design, frozen);
     verify resolves material by id — `KEY_UNKNOWN` refusal when the id is
     not in the keyring, `KEY_RETIRED` when past the key's retire-at;
   - `rotateKeyring` operation: new current key (id + material via the
     SecureRandom port), old key keeps a verify-grace window, then retired;
   - a labelled fixture provider + a file-backed provider (path supplied by
     the host; file contents NEVER read into errors or logs).

   - `SecureRandom` port: `randomHex(n)`, `credentialSalt()` (16+ bytes);
   - the authenticated composition generates salts via the port (the pure
     `issueCredential` kernel keeps its caller-supplied contract UNCHANGED
     — grow-only, zero edits to F370A semantics);
   - a deterministic test impl (fixed stream — determinism battery) + the
     production binding note (node:crypto at the host boundary only).
3. **Session revocation** (`packages/identity/src/session-revocation.ts`):
   - add `jti` (token id) to the signed claims — THIS LANE'S SANCTIONED

   - `SessionRevocationRegistry` port + the in-memory impl (labelled):
     `revoke(jti, at)`, `isRevoked(jti)`, `revokeActor(actorId, at)`;
   - `verifySessionWithRevocation` composition: `verifySignedSession`
     FIRST (signature/expiry precede revocation — deterministic order,
     machine-asserted), then the registry check → `REVOKED` verdict;
     verdicts-as-data, verify stays total (never throws).
