## Procedure

1. Branch `work/f310b` from actual `main` HEAD. Record the SHA.
2. First run: push (even evidence-only WIP) and let CI execute at the base
   tree. Analyze the full-build job log:
   - `@zcode/web` (packages/web, vite build) — previously OOM at ~2.3GB
     available; 16GB should clear it. If it fails for a REAL reason, record.
   - `@zcode/desktop`, `@zcode/server` — previously ENOENT under
     `--ignore-scripts`; scripts are ON here. Record what actually happens.
   - `apps/zcode-cli` (SEA) — previously missing SEA tooling. Node 24 + full
     install should provide it. Record the real outcome.
   - All FleetOS domain packages previously built clean (tsc --noEmit) —
     confirm they stay green.
3. Real failures in **your owned paths** (worker-b list): repair minimally
   and truthfully. Real failures in **TL-owned substrate paths**: DO NOT
   patch — produce per-failing-package reproduction + owner + scoped repair
   item (the handoff's format).
4. Iterate until the full build passes at your candidate, or until every
   remaining failure is documented with owner + reproduction + repair item.
5. Write `docs/evidence/F310B/report.md`:
   - exact tested SHA + branch; builder facts proving the ≥8GB class;
   - the command and its exit code; the run URL;
   - a per-package outcome table (all packages; especially the four
     previously-failing substrate targets);
   - the standalone FleetOS shell build result reported SEPARATELY;
   - B-2 CLOSED at this SHA, or OPEN with per-target repair items.
6. Commit evidence to `work/f310b`, push. Final message: **"FINAL REPORT"**
   with SHA, run URL, BUILD_EXIT, and B-2 status.

  The gate is the FULL recursive build.
- **Ownership is strict:** substrate paths are TL-owned; your repairs stay in
  worker-b paths or are proposals only.
- **Evidence is machine output.** The public run page + your quoted tables.
- **Grow-only:** no test removals.
